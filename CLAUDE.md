# Faiz & Muna Journal (`faiz-muna-journal`)

Repo: https://github.com/FaizGhazali/faiz-muna-journal · App title shown to users: "Our Journal" (becomes "<name> & <name>'s Journal" after first-run setup).

A private two-person weight / BMI / exercise journal. Installable PWA, hosted on Firebase, data in Firestore.

## Stack

- **No build step, no framework.** `public/` is served as-is: `index.html`, `app.js` (the entry ES module) plus the other modules described below, `styles.css`, `sw.js`, `manifest.webmanifest`.
- Firebase JS SDK 10.14.1 is imported straight from `https://www.gstatic.com/firebasejs/...` in `app.js`. There is no bundler and no `node_modules` import in the browser code.
- The only npm dependency is `firebase-tools` (dev), used for emulators and deploy.
- Firebase project: `faiz-muna-journal-c43ab` (`.firebaserc`).

## Commands

```bash
npm ci                 # install firebase-tools
npm run dev            # local app + Auth/Firestore emulators (needs Java 11+)
npm run icons          # regenerate public/icon-192.png and icon-512.png
npx firebase deploy    # deploy hosting + firestore rules to production
```

`npm run dev` serves the app at http://localhost:5000 and the emulator UI at http://localhost:4000. Emulator data is thrown away on exit.

## How it works

- **Auth:** one shared family login. The email is the fixed constant `FAMILY_EMAIL` in `app.js`; the user types only the password. `firestore.rules` allows read/write for that single production UID and nobody else.
- **Local mode:** when the hostname is `localhost` / `127.0.0.1`, `app.js` uses a demo config (`demo-journal`) and connects to the Auth emulator on **9099** and the Firestore emulator on **8085**. These ports are hard-coded in `app.js` and must match the `emulators` block in `firebase.json`. The service worker is not registered locally.
- **Local rules:** the production rules pin one UID, which an emulator account never has, so `npm run dev` uses `firebase.dev.json` → `firestore.dev.rules` (any signed-in user). Never deploy with the dev config.
- **Local login:** the emulator starts empty. Create the user `family@journal.invalid` with any password in the emulator UI (Authentication tab), then sign in with that password.
- **Production config** comes from `/__/firebase/init.json`, which Firebase Hosting serves automatically. No API keys live in the repo.
- **Data model:**
  - `config/people` → `{ people: [{ id: "p1"|"p2", name, age, sex, cm, born? }] }`. Written by the first-run setup screen. `born` (`YYYY-MM-DD`) is added later on the Fitness detail page and labels each dot with the age on that run.
  - Diary collections (`diary`, `diaryPhotos`, `diaryStyle`): see **Dearly** below.
  - `entries/{person}_{YYYY-MM-DD}` → `{ person, date, weight?, minutes?, run?, note?, mood? }`. One entry per person per day; saving again on the same day merges into it. `mood` (1–5, hard → great) is written on its own by the mood card / page with `setDoc(..., { merge: true })`; the entry form keeps it when saving. `run` → `{ source: "coros", km, secs, hr, pace?, effort?, hrMax?, hrr?, load?, cadence?, stride?, power?, ground?, kcal? }` (paces in seconds per km). `minutes` is set from the run time; older entries have typed minutes and no `run`.
  - `activities/{auto id}` → `{ owner: "p1"|"p2", title, type: skill|task|explore|cook|habit, status: inbox|active|paused|done|archived, created, ...optional }`. Optional fields by type: `note`, `minutes`, `due` (task), `steps: [{text, done}]` + `lastDone` (skill), `location` (explore), `url` + `favourite` (cook), `days: [0-6]` (habit; missing = every day), `snoozed` (hidden through that date), `doneOn`.
  - `habitDays/{person}_{YYYY-MM-DD}` → `{ owner, date, done: [habit ids], skipped: [habit ids] }`. History is kept; "today" is just a new doc id.
  - `moves/{auto id}` → `{ owner, item, type, act: done|later|another, date, hour }`. One per press of Done / Not now / Suggest another on the card, and per habit ticked. Only the last 180 days are loaded.
  - `visits/{country code}` → `{ n }`: the landing page visitor count. The only public collection: `firestore.rules` lets anyone read it and add exactly 1 to one country. `public/visits.js` (pure, tested) guesses the country from the browser time zone (no IP lookup); `visitors()` in `app.js` counts each device once (`localStorage` `journal-visited`, bots skipped) and fills `#visitors` on the landing page.
- **Activities ("Your Next Move"):** `public/suggest.js` is the rule-based recommender (pure, no Firebase/DOM; tune scores there). `public/activities.js` owns the dashboard card, the habit checklist and the `#activities` page. New items always land in `inbox` (Ideas) and are only suggested once started. Suggestions learn from each person's `moves`: `learn()` / `learned()` in `suggest.js` add a capped nudge for items they usually say yes to, the time of day and weekday they usually do that thing, and lighter items after exercise that day. The rules (due dates etc.) still lead. The manifest shortcut "What's next?" opens `/#next`. Per-device UI state (current suggestion, recently shown, today's "Suggest another" skips, selected person) is in `localStorage` under `journal-*` keys.
- **Exercise / fitness:** exercise is logged by adding a COROS run picture in the entry form. `public/coros.js` reads it on the device with Tesseract.js (pinned jsDelivr import, loaded on demand) and `parseCoros` picks out the numbers; the picture is never uploaded or stored, and the user checks the numbers before saving. `public/fitness.js` (pure; tune the formula there) turns each run into a score from pace vs heart rate, and the graph line is a moving average. Scores are worked out when drawing, never stored.
- **Fitness detail page:** "Show more detail" on a fitness card opens `#fitness/<person id>` (views are switched by hash in `showView()` in `activities.js`). `public/fitdetail.js` draws zero to four read-only graph cards, picked with chips at the top (choice kept per device in `localStorage` `journal-fitgraphs`): Weight vs pace (scatter), Weight vs distance (bars: average km per run in each weight band from `weightBands()`; bars under 3 runs are faint), Pace over time and Distance over time (scatters by date). Each card has First / Best (or Longest) / Now tiles and the date-shaded dots or bars. `public/runweight.js` (pure, unit-tested) pairs each run with a same-day weight or the nearest weigh-in within 7 days (tie → earlier; never interpolated) and fits the least-squares line; no line under 3 runs, "low confidence" under 8. Tests: `npm test` (Node's built-in runner, `tests/*.test.mjs`).
- **Mood:** each person rates their own day with five faces; the app never guesses mood from other data. The "Yesterday" card on the dashboard (`#moodCard`, follows the "For" person) shows the rating, a reminder line (run, habits), a quote and the face picker. "Mood history →" opens `#mood`: week / month / year tiles, a year in pixels  (months × days; tap a square to rate or change that day. The first tap also opens the "Mood mix" card inside it: five bars showing what share (%) of the rated days in that month were hard … great; tapping the same day again switches to its week, chips switch week / month / year. While it is open, Year in pixels jumps to its year and dims every day outside the counted period. Data from `moodMix()` in `mood.js`; the card is built once and updated in place so bars and numbers animate) and "What goes with your good days" (average mood with vs without exercise, most habits, a Next Move, a weigh-in; needs `MIN_DAYS` rated days and 3 on each side). `public/mood.js` is pure (quotes, stats; tests in `tests/mood.test.mjs`); `public/moodui.js` draws the card and page; `habitFacts()` in `activities.js` supplies habit and move facts. Mood colours are `--m1`…`--m5` in `styles.css` (cool blue for hard, warm orange for great; colour-blind safe). Quotes are our own words; never paste in copyrighted quotes.
- **Meals journal + wheel:** the round button at the bottom right (`#wheelBtn`) opens a weapon-wheel menu of journals (`JOURNALS` in `public/mealsui.js`): tap it then tap a journal (holding and sliding to one also works; the click a phone sends after the opening tap is ignored by `ghost()`). Meals, Weight and Diary are real; the rest are empty placeholder slots that open `#soon`. A ⋯ button (`#wheelMore`) in the wheel's top-right corner opens an extras menu (`#wheelMenu`: Show me how → `#guide`, Meal sets → `#mealsets`, Backup scrolls to the backup panel, Show tips again). A cloud tip (`#wheelTip`) points at ⋯ each time the wheel opens until it has shown `TIP_VIEWS` (5) times, "Don't show again" is ticked, or ⋯ is used (`localStorage` `journal-tip-more`: count or `off`); nobody is forced to tick anything. `#guide` is the "Show me how" page (`public/tour.js`): a searchable list of how-tos (`GUIDES`); tapping one opens a sheet (`#guideSheet`) with what it covers and, for those with `steps`, "Start walkthrough". A walkthrough dims the screen, lights up one part (`spot`), rings a field (`point`) and draws a dotted arrow from its bubble to it; a step ends when `done()` turns true (something the person did) or on Next (`ready()` can hold it). If `lost()` stays true for `LOST_MS` it goes back to `backTo`. A rAF loop re-measures every frame, so it follows scrolling, the wheel opening and the phone keyboard. The finish card offers "Look around" (free roam) or "More how-tos" (`#guide`). Only "Log your weight" (`WEIGH`) has steps so far; the others are quick tips. While one runs, `html.touring` keeps the wheel tip away. To add a walkthrough, give a `GUIDES` entry `steps`. Every journal shares the top: `#shared` in `index.html` holds Your Next Move, habits, Yesterday and one card per person (`#people`). Each person card has weight/BMI on top, then one `.pextra[data-journal]` part per journal (`JOURNAL_PARTS` in `app.js`); `showView()` sets `#people[data-journal]` so only the picked journal's part shows (Weight → fitness score + exercise minutes, Meals → Calories), and fires a `journalchange` event so hidden charts redraw at their real width. A new journal adds its id to `JOURNAL_PARTS` and fills `<id>Slot-<person id>`. The pick is kept per device in `localStorage` `journal-type` (default `meals`), and the Dashboard tab / empty hash shows it (`journalView()`, used by `showView()` in `activities.js`): `meals` view or the old `home` weight dashboard. Data: `foods/{auto id}` → `{ name, kcal, carb, protein, fat }` per 100 g and `mealSets/{auto id}` → `{ name, items: [{ food, g }] }` are shared by both people; `meals/{auto id}` → `{ person, date, slot: breakfast|lunch|dinner|snack, name, set?, items: [{ food, name, g, kcal, carb, protein, fat }], at }` copies the numbers so editing a food never changes history (last 180 days loaded). `public/meals.js` is pure (tests in `tests/meals.test.mjs`): `usual()` = median of the person's last 5 portions of a food, used to fill the grams once weighed `LEARN_AFTER` (3) times. The meal card has its own Who switch (starts from "For"). Meal sets and foods are edited on their own page, `#mealsets`. A set may list `slots` (the meals it's eaten at); the card offers only sets that fit the picked meal (`fitsSlot()`), with the rest behind "Other meals' sets". "Save as a set" tags it with the current meal. **Calories part** (in each person card, `mealsSlot-<id>`): the last 14 days of kcal eaten vs a range per day: burn = typed watch total from `burns/{person}_{date}` → `{ person, date, kcal }`, else Mifflin-St Jeor resting burn × `ACTIVITY` + that day's run kcal; `intakeRange()` aims about `PACE_KCAL` under burn when BMI ≥ 25, ±200 when normal, over when < 18.5, never under 1200/1500. Unlogged days are left out, never counted as zero (logging is optional; keep the copy forgiving). Tapping a bar opens that day. A "14 days / Year" switch (kept per device in `localStorage` `journal-calview`) swaps the bars for a GitHub-style strip of the last 53 weeks (`yearHtml()`): one square per day coloured by `shadeOf()` (far under / under / in / over / far over, `FAR` = 400 kcal past the range; not logged = grey), with tiles from `yearStats()` (days logged, % in range, average, best streak; unlogged days never break a streak; today isn't counted). Meals and burns load 380 days for this.
- **Dearly (diary journal):** the "Diary" slot on the wheel (`journal-type` `diary`; `journalView()` returns `diary`). `#diary` is one view whose page comes from the hash, drawn by `public/diaryui.js`: `#diary` dashboard (welcome, stats, On this day, memories with search / month / tag / favourite / sort and "Show more" by `PAGE`), `#diary/write`, `#diary/edit/<id>`, `#diary/read/<id>` (older / newer), `#diary/ai` (writer, About you, style, privacy, Recently deleted, paper colour). The shared top (`#shared`) is hidden in the diary to keep it calm. It follows the "For" person. Data: `diary/{auto id}` → `{ person, date, title?, body, notes?, mood?, tags, fav, cover? (small thumbnail), photos?: [ids], ai?, noStyle?, created, updated, deleted? (ms, Recently deleted; purged after `KEEP_DELETED_DAYS`) }`; `diaryPhotos/{auto id}` → `{ entry, person, data (JPEG data URL ≤ ~700 KB), w, h }`; `diaryStyle/{person}` → `{ on, since?, about?, dismissed?: [suggestion keys] }` (always write with `merge`). Drafts autosave per device in `localStorage` `journal-diary-draft-<pid>` / `journal-diary-edit-<id>`. Pure logic: `public/diary.js` and `public/writestyle.js` (tests in `tests/diary.test.mjs`). **The AI writer runs in the browser** with WebLLM 0.2.86 (pinned jsDelivr import, loaded only when used) on WebGPU in a Web Worker (`public/aiworker.js`); `public/localai.js` has `MODELS` (Qwen2.5 0.5B / 1.5B / 3B, f16 or f32 by device), the support check, download / load / write / remove. No server, no API key, no paid API, ever: never add a cloud fallback. The model is fetched only when someone taps Download, from huggingface.co, and lives in Cache Storage `webllm/*`, which `sw.js` must never delete (it clears only `journal-*` caches). Prompt rules (`buildMessages`): use only the notes; each note keeps its own language, judged by grammar words (`noteLang`: Malay with English words stays Malay, Manglish stays Manglish, never translate); the style profile never sets the language; spelling and grammar are corrected (casual, not formal): `expandShort()` spells out texting short forms (`SHORT_FORMS`: ckp → cakap, x → tak) before the model sees the notes, because small models copy rather than follow the rule, and the checks accept corrected spellings (`sameWord`); "About you" is background only. After writing, `unsupported()` flags words not in the notes and `dropped()` lists the person's own Malay / Manglish words that got lost; the person always edits before saving. One numbered sentence per note: the model replies `1. …` per note and `cleanOutput()` checks each sentence against its own note (`strayed()`: any word the note never gave, a language switch, or far longer), putting the note itself back when one strays, then joins them into paragraphs (pass `done = false` while streaming). Tested on Qwen2.5-3B: free-form entries translated English words inside Malay ("just boring" → "hanya bosan") and wrote nonsense; numbered + checked never did. One worked example per language (`EXAMPLES`), because the model copies it (a Malay-only example turned English notes into Indonesian-style Malay; "Harini" became "Harimau", so examples say "Hari ni"). The demo server (`demo_messages`) uses the same shape; the app sends it `{notes, lang}` (`demoBody()` in `cloudai.js`). "Suggestions from your entries" on `#diary/ai` (`aboutSuggestions()` / `addToAbout()`): names seen in `SUGGEST_MIN`+ entries are asked about ("Who is Lina to you?", the person types the answer); frequent words and language mix are offered once (keys `words`, `lang`). Counting only, never the model, never moods; nothing is added without a tap; the dashboard link shows a count badge. Style learning is off until the person turns it on and learns only from entries they wrote themselves (`styleSource`: not `ai`, not `noStyle`, since `since`). **Cloud writer (optional, free):** `modal/dearly_writer.py` runs Qwen2.5-3B (default on CPU with llama.cpp, no card needed; `GPU` = T4/L4 is faster but Modal wants a card on file, still free credit) within Modal's free monthly credit (spending limit $0). A CPU front door checks the family's Firebase ID token (`/write`, full prompt from the app) or serves the demo (`/demo`: notes only, server-built prompt, capped per visitor and per day in a Modal Dict); refused requests never wake the GPU. `public/cloudai.js` holds `CLOUD_URL` (empty = hidden; Modal address or localhost for testing); the choice is per device (`journal-ai-where`, consent `journal-ai-cloud-ok`), offered in the editor wherever the on-phone writer can't run or needs a download. `app.js` passes `token` (Firebase ID token) and `demo` to `initDiary`. Setup: `docs/dearly-modal.md`. Full notes, models, limits and the test report: `docs/dearly.md`.
- **Fold cards:** `public/collapse.js` adds a round knob (`.fold`) on the middle of the top edge of every card (`#app .view .panel`, `.person`), where no card has content of its own. Holding it ~550 ms (the ring fills) folds the card; on touch / pen the whole top row works too (`inTop()`: first content row, 56–120 px; buttons, links and inputs there keep working), and holding a folded card opens it. A folded card is one line showing `data-title` (`titleOf()`). A short tap on the knob only shows a "Hold me" bubble, so scrolling never folds anything. Tapping a folded card opens it. Folded cards are kept per device in `localStorage` `journal-folded`, keyed by the card's id / aria label / title (`keyOf()`). Cards are redrawn with innerHTML, so a MutationObserver puts the button and state back. The tutorial card `#foldHint` (under the tabs) shows until "Got it" is ticked (`journal-foldhint`).
- **Graph zoom:** `public/zoom.js` zooms into the data, not the picture: pinch (touch) or Ctrl + scroll / trackpad pinch (computer) narrows the visible x range, and the chart redraws only that stretch with its side scale fitted to the points in view (weight to 0.1 kg). One-finger / mouse drag pans once zoomed; double-tap, double-click or "Reset zoom" resets. A chart opts in by reading `xWindow(host)` (fractions `{ a, b }` of its full range) while drawing and calling `zoomable(host, plotLeft, plotRight, redraw)` after; the window is kept by host id. Used by the weight and fitness charts in `app.js` and the scatters in `fitdetail.js` (not the calorie bars or weight-band bars). Touch move/end listeners sit on the touched element because redraws detach it.
- **Open where you left off:** `showView()` saves the page hash in `localStorage` `journal-page` (`RESUME` in `activities.js`: activities, mood, meal sets, fitness detail); opening the app with no hash goes back there. The journal (Meals / Weight) is kept separately by the wheel (`journal-type`).
- **Backup:** `public/backup.js` saves every collection to a `journal-backup-YYYY-MM-DD.json` file (`{ app: "our-journal", version, exported, data: { collection: { docId: fields } } }`) and loads one back. Loading only adds or replaces docs by id; it never deletes.
- **Landing / SEO:** under the sign-in form, `<main id="landing">` in `index.html` is a scroll-animated tour for visitors and search engines (hidden by CSS whenever `#loading`, `#setup` or `#app` shows). Its words are plain static HTML so crawlers read them; `public/landing.js` only animates the sample demos (`--p` 0→1 per `.scene` over one screen of scroll, `data-at` / `data-from`/`data-to` hooks). Use made-up sample numbers, never real family data. When features change, update the scene text, the "What's new" list, the FAQ and the matching JSON-LD in `<head>`, and `lastmod` in `sitemap.xml`.
- **Demo ("Try the demo"):** a button under the sign-in form and at the end of the tour sets `sessionStorage` `journal-demo=1` and reloads. In demo mode `app.js` never starts Firebase Auth or Firestore: `useMemory()` in `public/fs.js` switches every Firestore call to `public/memdb.js`, an in-memory stand-in (only the calls the app uses) saved to `sessionStorage` `journal-demo-db`, so it survives a reload and dies with the tab. It is seeded from `public/sample.js` (pure; made-up people "Amir" and "Lina", 12 weeks ending today, repeatable random numbers). The inline script in `<head>` swaps `localStorage` for `sessionStorage` in demo mode so per-device keys never touch the family's own. A bar at the top offers "Start over" and "Exit demo". **All app files import Firestore functions from `./fs.js`, not gstatic** (only `app.js` imports `initializeFirestore` and friends directly). If you start using a new Firestore function, add it to `fs.js` and `memdb.js`.
- **Bot protection:** demo visitors never reach Firebase. `firestore.rules` refuses everyone but the family UID. `APP_CHECK_KEY` in `app.js` turns on Firebase App Check (reCAPTCHA Enterprise) when set; it's empty until the key is made in the Firebase console. Only switch App Check *enforcement* on in the console after the live site has been sending verified requests, or the family is locked out.
- **Offline:** Firestore persistent cache holds the data; `sw.js` caches the app shell (network-first for own files, cache-first for the versioned gstatic SDK files). Signing out clears the local Firestore cache.

## Conventions

- Keep it dependency-free and build-free. Plain DOM, template strings, `$()` = `getElementById`.
- Everything user-entered that goes into `innerHTML` must pass through `esc()`.
- BMI ranges are WHO adult cut-offs (18.5 / 25 / 30); the footer also mentions the Asian 22.9 cut-off. Goal pace is `PACE` kg/week, weekly exercise target is `WEEKLY_MINUTES`.
- If you add or rename a file in `public/`, add it to `SHELL` in `sw.js` and bump `CACHE` (e.g. `journal-v2` → `journal-v3`).
- Dates are local-time `YYYY-MM-DD` strings; use the `iso` / `parse` / `dayNum` helpers rather than `Date` parsing.
- UI copy is plain and short, written for two non-technical users on phones. Check layouts at phone width.

## Care points

- `npm run dev` goes through `tools/dev.js`, which points Java's local-socket folder at `~/.cache/firebase/uds`. On this machine the Firestore emulator otherwise crashes with "Unable to establish loopback connection" because Java can't open sockets in `%TEMP%`.
- `firestore.rules` is the only thing protecting the data. Changing the UID or loosening the match locks the family out or opens the journal — do not edit or deploy rules without being asked.
- `npx firebase deploy` goes straight to the live site the family uses. Only deploy when asked.
- **Pushing to `main` deploys too.** `.github/workflows/deploy.yml` publishes `public/` (hosting only, never rules) using the repo secret `FIREBASE_SERVICE_ACCOUNT_FAIZ_MUNA_JOURNAL_C43AB`. So a push is a release: only push to `main` when asked.
- This repo lives at `Documents\Faiz\2026\faiz-muna-journal`, beside (not inside) the unrelated `Creator` repo. Keep it out of `Creator`.
