# Faiz & Muna Journal (`faiz-muna-journal`)

Repo: https://github.com/FaizGhazali/faiz-muna-journal · App title shown to users: "Our Journal" (becomes "<name> & <name>'s Journal" after first-run setup).

A private two-person weight / BMI / exercise journal. Installable PWA, hosted on Firebase, data in Firestore.

## Stack

- **No build step, no framework.** `public/` is served as-is: `index.html`, `app.js` (the entry ES module) plus the other modules described below, `styles.css`, `sw.js`, `manifest.webmanifest`.
- **Folder layout of `public/`**, by role (which folder a file goes in says what it may depend on):
  - root: only what the browser loads by address: `index.html`, `app.js` (wiring only), `sw.js` (must stay at the root to control the whole site), `styles.css`, manifest, icons, `robots.txt`, `sitemap.xml`.
  - `core/`: **reusable building blocks** that know nothing about any journal: `util.js` (shared helpers), `fs.js` + `memdb.js` (Firestore or the demo's in-memory copy), `confirm.js`, `face.js`, `zoom.js`, `collapse.js`, `journal.js`. Imports only other `core/` files.
  - `logic/`: **pure rules**, no DOM / Firestore / `localStorage`, each unit-tested in `tests/`: `suggest`, `fitness`, `runweight`, `mood`, `reflect`, `meals`, `stocky`, `diary`, `writestyle`, `bmi`, `visits`, `ledger`, `ledgerimport`, `moneyplan`. Imports only `logic/` and `core/util.js`.
  - `features/<journal>/`: **each journal's screens**: `weight/` (person cards, charts, entry form, COROS reader, fitness detail), `meals/`, `diary/` (Dearly, one file per page plus its AI writer), `stocky/`, `ledger/` (Ledger: entry `ledgerui.js`, `plan.js`, `import.js`, `trends.js`, `rules.js`, `seeds.js`), `mood/`, `activities/` (Next Move, habits, and `showView()` routing). Use `core/` and `logic/`; reach other features only through hooks passed in by `app.js` (or, today, a few direct imports such as `journalView` / `face`).
  - `shell/`: **standalone app-level pieces** that aren't a journal: `setup` (first run), `demo` + `sample` (the demo and its made-up data), `visitors`, `theme`, `install`, `widget`, `tour` ("Show me how"), `backup`, `landing` (the tour under the sign-in form).
  - A new file goes in the folder that matches its role (a new journal = a new `features/<name>/`), and into `SHELL` in `sw.js`.
- Firebase JS SDK 10.14.1 is imported straight from `https://www.gstatic.com/firebasejs/...` in `app.js`. There is no bundler and no `node_modules` import in the browser code.
- The only npm dependency is `firebase-tools` (dev), used for emulators and deploy.
- Firebase project: `faiz-muna-journal-c43ab` (`.firebaserc`).

## Commands

```bash
npm ci                 # install firebase-tools
npm run dev            # local app + Auth/Firestore emulators (needs Java 11+)
npm run icons          # regenerate public/icon-192.png and icon-512.png
npx firebase deploy    # deploy hosting + firestore rules to production
```

`npm run dev` serves the app at http://localhost:5000 and the emulator UI at http://localhost:4000. Emulator data is thrown away on exit.

## How it works

- **Auth:** one shared family login. The email is the fixed constant `FAMILY_EMAIL` in `app.js`; the user types only the password. `firestore.rules` allows read/write for that single production UID and nobody else.
- **Local mode:** when the hostname is `localhost` / `127.0.0.1`, `app.js` uses a demo config (`demo-journal`) and connects to the Auth emulator on **9099** and the Firestore emulator on **8085**. These ports are hard-coded in `app.js` and must match the `emulators` block in `firebase.json`. The service worker is not registered locally.
- **Local rules:** the production rules pin one UID, which an emulator account never has, so `npm run dev` uses `firebase.dev.json` → `firestore.dev.rules` (any signed-in user). Never deploy with the dev config.
- **Local login:** the emulator starts empty. Create the user `family@journal.invalid` with any password in the emulator UI (Authentication tab), then sign in with that password.
- **Production config** comes from `/__/firebase/init.json`, which Firebase Hosting serves automatically. No API keys live in the repo.
- **Data model:**
  - `config/people` → `{ people: [{ id: "p1"|"p2", name, age, sex, cm, born? }] }`. Written by the first-run setup screen. `born` (`YYYY-MM-DD`) is added later on the Fitness detail page and labels each dot with the age on that run.
  - Diary collections (`diary`, `diaryPhotos`, `diaryStyle`): see **Dearly** below.
  - `entries/{person}_{YYYY-MM-DD}` → `{ person, date, weight?, minutes?, run?, note?, mood? }`. One entry per person per day; saving again on the same day merges into it. `mood` (1–5, hard → great) is written on its own by the mood card / page with `setDoc(..., { merge: true })`; the entry form keeps it when saving. `run` → `{ source: "coros", km, secs, hr, pace?, effort?, hrMax?, hrr?, load?, cadence?, stride?, power?, ground?, kcal? }` (paces in seconds per km). `minutes` is set from the run time; older entries have typed minutes and no `run`.
  - `activities/{auto id}` → `{ owner: "p1"|"p2", title, type: skill|task|explore|cook|habit, status: inbox|active|paused|done|archived, created, ...optional }`. Optional fields by type: `note`, `minutes`, `due` (task), `steps: [{text, done}]` + `lastDone` (skill), `location` (explore), `url` + `favourite` (cook), `days: [0-6]` (habit; missing = every day), `snoozed` (hidden through that date), `doneOn`.
  - `habitDays/{person}_{YYYY-MM-DD}` → `{ owner, date, done: [habit ids], skipped: [habit ids] }`. History is kept; "today" is just a new doc id.
  - `moves/{auto id}` → `{ owner, item, type, act: done|later|another, date, hour }`. One per press of Done / Not now / Suggest another on the card, and per habit ticked. Only the last 180 days are loaded.
  - `nextMove/{person}` → `{ person, item, title, type, why, date, updated }`: each person's current "Your next move" for the Android widget (`title: null` = nothing to suggest, `why` then holds the hint). Written by `publishMoves()` in `activities.js` for both people, only when it changed; never written by hand. See **Android widget**.
  - `visits/{country code}` → `{ n }`: the landing page visitor count. The only public collection: `firestore.rules` lets anyone read it and add exactly 1 to one country. `public/logic/visits.js` (pure, tested) guesses the country from the browser time zone (no IP lookup); `visitors()` in `public/shell/visitors.js` counts each device once (`localStorage` `journal-visited`, bots skipped) and fills `#visitors` on the landing page.
- **Activities ("Your Next Move"):** `public/logic/suggest.js` is the rule-based recommender (pure, no Firebase/DOM; tune scores there). `public/features/activities/activities.js` owns the dashboard card, the habit checklist and the `#activities` page. New items always land in `inbox` (Ideas) and are only suggested once started. Suggestions learn from each person's `moves`: `learn()` / `learned()` in `suggest.js` add a capped nudge for items they usually say yes to, the time of day and weekday they usually do that thing, and lighter items after exercise that day. The rules (due dates etc.) still lead. The manifest shortcut "What's next?" opens `/#next`. Per-device UI state (current suggestion, recently shown, today's "Suggest another" skips, selected person) is in `localStorage` under `journal-*` keys.
- **Exercise / fitness:** exercise is logged by adding a COROS run picture in the entry form. `public/features/weight/coros.js` reads it on the device with Tesseract.js (pinned jsDelivr import, loaded on demand) and `parseCoros` picks out the numbers; the picture is never uploaded or stored, and the user checks the numbers before saving. `public/logic/fitness.js` (pure; tune the formula there) turns each run into a score from pace vs heart rate, and the graph line is a moving average. Scores are worked out when drawing, never stored.
- **Fitness detail page:** "Show more detail" on a fitness card opens `#fitness/<person id>` (views are switched by hash in `showView()` in `activities.js`). `public/features/weight/fitdetail.js` draws zero to four read-only graph cards, picked with chips at the top (choice kept per device in `localStorage` `journal-fitgraphs`): Weight vs pace (scatter), Weight vs distance (bars: average km per run in each weight band from `weightBands()`; bars under 3 runs are faint), Pace over time and Distance over time (scatters by date). Each card has First / Best (or Longest) / Now tiles and the date-shaded dots or bars. `public/logic/runweight.js` (pure, unit-tested) pairs each run with a same-day weight or the nearest weigh-in within 7 days (tie → earlier; never interpolated) and fits the least-squares line; no line under 3 runs, "low confidence" under 8. Tests: `npm test` (Node's built-in runner, `tests/*.test.mjs`).
- **Mood:** each person rates their own day with five faces; the app never guesses mood from other data. A mood picked on a Dearly diary entry counts as a rating too: `dayMoods()` in `mood.js` gathers the face rating (`entries.mood`) and every live diary entry's `mood` for the day, and `moodMap(entries, pid, diary)` gives each day their average rounded to a face (several entries a day are averaged). Nothing is copied into `entries`; it's worked out when drawing (`diaryList()` from `diaryui.js` is passed to `initMood`, and the diary snapshot calls `refreshMood`). Tapping a day on Year in pixels opens its flashcard (`renderDay()` in `moodui.js`: the mood and what it averages, that day's diary entries linking to `#diary/read/<id>`, run, weight, note, habits, Next Move, and the faces to rate). **Reflections:** `public/logic/reflect.js` (pure, tests in `tests/reflect.test.mjs`) is the engine: `reflections()` makes scored cards (comfort after a hard day, On this day, a week / month ago, bright spot, week trend, what lifts your days, a tag on good days, writing streak, this month); `pickReflection()` picks the dashboard one (`#reflectCard` in `#shared`: score ≥ 90 leads, otherwise one of the top three by date; "Another" steps through). The Mood page lists them all in `#mdReflect`; "See the day" opens that day's flashcard (`openDay()`). The "Yesterday" card on the dashboard (`#moodCard`, follows the "For" person) shows the rating, a reminder line (run, habits), a quote and the face picker. "Mood history →" opens `#mood`: week / month / year tiles, a year in pixels  (months × days; tap a square to rate or change that day. The first tap also opens the "Mood mix" card inside it: five bars showing what share (%) of the rated days in that month were hard … great; tapping the same day again switches to its week, chips switch week / month / year. While it is open, Year in pixels jumps to its year and dims every day outside the counted period. Data from `moodMix()` in `mood.js`; the card is built once and updated in place so bars and numbers animate) and "What goes with your good days" (average mood with vs without exercise, most habits, a Next Move, a weigh-in; needs `MIN_DAYS` rated days and 3 on each side). `public/logic/mood.js` is pure (quotes, stats; tests in `tests/mood.test.mjs`); `public/features/mood/moodui.js` draws the card and page; `habitFacts()` in `activities.js` supplies habit and move facts. Mood colours are `--m1`…`--m5` in `styles.css` (cool blue for hard, warm orange for great; colour-blind safe). Quotes are our own words; never paste in copyrighted quotes.
- **Meals journal + wheel:** the round button at the bottom right (`#wheelBtn`) opens a weapon-wheel menu of journals (`JOURNALS` in `public/features/meals/mealsui.js`): tap it then tap a journal (holding and sliding to one also works; the click a phone sends after the opening tap is ignored by `ghost()`). Meals, Weight, Dearly (the diary) and Stocky (groceries) are real; the rest are empty placeholder slots that open `#soon`. A ⋯ button (`#wheelMore`) in the wheel's top-right corner opens an extras menu (`#wheelMenu`: Show me how → `#guide`, Meal sets → `#mealsets`, Backup scrolls to the backup panel, Show tips again). A cloud tip (`#wheelTip`) points at ⋯ each time the wheel opens until it has shown `TIP_VIEWS` (5) times, "Don't show again" is ticked, or ⋯ is used (`localStorage` `journal-tip-more`: count or `off`); nobody is forced to tick anything. `#guide` is the "Show me how" page (`public/shell/tour.js`): a searchable list of how-tos (`GUIDES`); tapping one opens a sheet (`#guideSheet`) with what it covers and, for those with `steps`, "Start walkthrough". A walkthrough dims the screen, lights up one part (`spot`), rings a field (`point`) and draws a dotted arrow from its bubble to it; a step ends when `done()` turns true (something the person did) or on Next (`ready()` can hold it). If `lost()` stays true for `LOST_MS` it goes back to `backTo`. A rAF loop re-measures every frame, so it follows scrolling, the wheel opening and the phone keyboard. The finish card offers "Look around" (free roam) or "More how-tos" (`#guide`). Only "Log your weight" (`WEIGH`) has steps so far; the others are quick tips. While one runs, `html.touring` keeps the wheel tip away. To add a walkthrough, give a `GUIDES` entry `steps`. Each person card has weight/BMI on top, then one `.pextra[data-journal]` part per journal (`JOURNAL_PARTS` in `weightui.js`); `showView()` sets `#people[data-journal]` so only the picked journal's part shows (Weight → fitness score + exercise minutes, Meals → Calories), and fires a `journalchange` event so hidden charts redraw at their real width. A new journal adds its id to `JOURNAL_PARTS` and fills `<id>Slot-<person id>`. The pick is kept per device in `localStorage` `journal-type` (default `meals`), and the Dashboard tab / empty hash shows it (`journalView()` in `public/core/journal.js`, used by `showView()` in `activities.js`; the wheel writes it with `setJournal()`): `meals` view or the old `home` weight dashboard. Data: `foods/{auto id}` → `{ name, kcal, carb, protein, fat }` per 100 g and `mealSets/{auto id}` → `{ name, items: [{ food, g }], slots?, made?: cooked|bought, ingredients?: [{ item (Stocky pantry id), qty }], serves?, price? }` are shared by both people; `meals/{auto id}` → `{ person, date, slot: breakfast|lunch|dinner|snack, name, set?, items: [{ food, name, g, kcal, carb, protein, fat }], at }` copies the numbers so editing a food never changes history (last 180 days loaded). `public/logic/meals.js` is pure (tests in `tests/meals.test.mjs`): `usual()` = median of the person's last 5 portions of a food, used to fill the grams once weighed `LEARN_AFTER` (3) times. The meal card has its own Who switch (starts from "For"). Meal sets and foods are edited on their own page, `#mealsets`. A set may list `slots` (the meals it's eaten at); the card offers only sets that fit the picked meal (`fitsSlot()`), with the rest behind "Other meals' sets". "Save as a set" tags it with the current meal. **Cooked / Bought:** a set's foods are what's on one plate (for calories); its "Made" part says how it's made. Cooked lists what goes in the whole pot from the Stocky Price book (amount in the item's unit) and how many plates it makes (`serves`, 1–`SERVES_MAX`); Bought has no ingredients, just an optional price for one plate. `setCost()` in `stocky.js` gives the cost a plate from each ingredient's `usualPrice()` (median normal price, sale only if nothing else); ingredients with no price yet are named ("no price yet for …"), never counted as free. Missing `made` = not said, no cost shown. `costLine()` in `mealsui.js` shows it on the sets page and under the plate (only while the plate is still that set). Each plate logged from a Cooked set uses its share of the pot (`qty / serves`) in Stocky's estimate (`cookedIn()` / `itemUse()`), and that plate's foods aren't counted again for those items; on `#stocky/plan` a Cooked set with ingredients is one pot per time and a Bought set needs nothing from home. Costs are worked out, never stored on meals. **Calories part** (in each person card, `mealsSlot-<id>`): the last 14 days of kcal eaten vs a range per day: burn = typed watch total from `burns/{person}_{date}` → `{ person, date, kcal }`, else Mifflin-St Jeor resting burn × `ACTIVITY` + that day's run kcal; `intakeRange()` aims about `PACE_KCAL` under burn when BMI ≥ 25, ±200 when normal, over when < 18.5, never under 1200/1500. Unlogged days are left out, never counted as zero (logging is optional; keep the copy forgiving). Tapping a bar opens that day. A "14 days / Year" switch (kept per device in `localStorage` `journal-calview`) swaps the bars for a GitHub-style strip of the last 53 weeks (`yearHtml()`): one square per day coloured by `shadeOf()` (far under / under / in / over / far over, `FAR` = 400 kcal past the range; not logged = grey), with tiles from `yearStats()` (days logged, % in range, average, best streak; unlogged days never break a streak; today isn't counted). Meals and burns load 380 days for this.

Drafts autosave per device in `localStorage` `journal-diary-draft-<pid>` / `journal-diary-edit-<id>`. **Tags:** chips in the editor (comma / Enter adds, spaces don't, so "part time" is one tag; `ed.tags` = chosen, `ed.tagText` = being typed). `tagKey()` in `util.js` (shared with Stocky kinds) ignores case, spaces, dashes and a plural "s", so near-copies are one tag: `parseTags(s, known)` saves the known spelling, and `tagStats()` / `showTags()` merge old near-copies when shown (data is never rewritten). `tagMatches()` gives `same`, `close` ("Did you mean": `looksLike()` = texting short form like mkan → makan, or 1–2 typos incl. swapped letters) and other matches; the memories search offers the same "Did you mean" when nothing matches. Pure logic: `public/logic/diary.js` and `public/logic/writestyle.js` (tests in `tests/diary.test.mjs`). **The AI writer runs in the browser** with WebLLM 0.2.86 (pinned jsDelivr import, loaded only when used) on WebGPU in a Web Worker (`public/features/diary/aiworker.js`); `public/features/diary/localai.js` has `MODELS` (Qwen2.5 0.5B / 1.5B / 3B, f16 or f32 by device), the support check, download / load / write / remove. No server, no API key, no paid API, ever: never add a cloud fallback. **Phones never run it:** `checkSupport()` returns `why: "mobile"` on phones and tablets (too slow / scrambled on the family's phones), so phones get the cloud writer offer or write themselves, and `clearAll()` removes any model a phone downloaded before. The model is fetched only when someone taps Download, from huggingface.co, and lives in Cache Storage `webllm/*`, which `sw.js` must never delete (it clears only `journal-*` caches). Prompt rules (`buildMessages`): use only the notes; each note keeps its own language, judged by grammar words (`noteLang`: Malay with English words stays Malay, Manglish stays Manglish, never translate); the style profile never sets the language; spelling and grammar are corrected (casual, not formal): `expandShort()` spells out texting short forms (`SHORT_FORMS`: ckp → cakap, x → tak) before the model sees the notes, because small models copy rather than follow the rule, and the checks accept corrected spellings (`sameWord`); "About you" is background only. After writing, `unsupported()` flags words not in the notes and `dropped()` lists the person's own Malay / Manglish words that got lost; the person always edits before saving. One numbered sentence per note: the model replies `1. …` per note and `cleanOutput()` checks each sentence against its own note (`strayed()`: any word the note never gave, a language switch, or far longer), putting the note itself back when one strays, then joins them into paragraphs (pass `done = false` while streaming). Tested on Qwen2.5-3B: free-form entries translated English words inside Malay ("just boring" → "hanya bosan") and wrote nonsense; numbered + checked never did. One worked example per language (`EXAMPLES`), because the model copies it (a Malay-only example turned English notes into Indonesian-style Malay; "Harini" became "Harimau", so examples say "Hari ni"). **Story mode** (default, on both the cloud and the device writer; per device `journal-ai-style` = story | close, `styleHtml()` chips in the editor and on `#diary/ai`; the device writer gets a little more temperature in Story): `buildMessages({ story: true })` asks for one to three sentences per note with colour but no new events (`STORY_EXAMPLES`), and `cleanOutput(..., story)` only puts a note back on a language switch or a runaway line, keeps folded notes from being added twice (`coveredIn`), and drops summary lines; what it added shows as "Added by the writer" (`unsupported`) for the person to check. Storytelling always added small details on every free model tried, so it's shown, not hidden. The demo server (`demo_messages`, `STORY_RULES`) uses the same shapes; the app sends it `{notes, lang, story}` (`demoBody()` in `cloudai.js`). "Suggestions from your entries" on `#diary/ai` (`aboutSuggestions()` / `addToAbout()`): names seen in `SUGGEST_MIN`+ entries are asked about ("Who is Lina to you?", the person types the answer); frequent words and language mix are offered once (keys `words`, `lang`). Counting only, never the model, never moods; nothing is added without a tap; the dashboard link shows a count badge. Style learning is off until the person turns it on and learns only from entries they wrote themselves (`styleSource`: not `ai`, not `noStyle`, since `since`). **Cloud writer (optional, free):** `modal/dearly_writer.py` runs Sailor2-8B, a Qwen2.5-based model trained for Southeast Asian languages (default on CPU with llama.cpp, no card needed; `GPU` = T4/L4 is faster but Modal wants a card on file, still free credit) within Modal's free monthly credit (spending limit $0). A CPU front door checks the family's Firebase ID token (`/write`, full prompt from the app) or serves the demo (`/demo`: notes only, server-built prompt, capped per visitor and per day in a Modal Dict); refused requests never wake the GPU. `public/features/diary/cloudai.js` holds `CLOUD_URL` (empty = hidden; Modal address or localhost for testing); the choice is per device (`journal-ai-where`, consent `journal-ai-cloud-ok`): `whereHtml()` puts a "This device / Cloud" switch at the top of the editor's writer box in every state and on `#diary/ai`, so either can be picked at any time. `app.js` passes `token` (Firebase ID token) and `demo` to `initDiary`. - **Stocky (groceries journal):** the "Stocky" slot on the wheel (`journal-type` `stocky`; `journalView()` returns `stocky`). One shared house stock and list, not per person, so `#shared` and the "For" switch are hidden. Pages by hash, drawn by `public/features/stocky/stockyui.js`: `#stocky` (Shopping list, then At home), `#stocky/item/<id>` (estimate and why, How much is left? A form someone has started filling in (`data-dirty`) isn't redrawn by live updates. ## Conventions

- **Clean code and architecture:** follow the `clean-code` skill (`.claude/skills/clean-code/SKILL.md`) by default for any non-trivial change: inspect before modifying, plan before implementing, build modularly (pure logic in tested modules, UI modules only draw and wire, `app.js` only wires), reuse before duplicating, test before finishing, and record decisions in this file.
- Keep it dependency-free and build-free. Plain DOM, template strings, `$()` = `getElementById`. Shared helpers (`$`, `esc`, the date helpers, `tagKey`) live in `public/core/util.js`; import them, never copy them. The mood face SVG is `face()` in `public/core/face.js`.
- **Every delete asks first** through `confirmDelete()` in `public/core/confirm.js` (title names the thing, body says what else goes, "Keep" is the default). Follow the `safe-delete` skill (`.claude/skills/safe-delete/SKILL.md`) by default whenever you add or change anything that deletes. Every journal uses it: entries, activities, meals, foods, meal sets, the typed watch burn, Dearly (delete, delete forever, discard draft, start fresh, remove photo, reset style) and Stocky. It answers from the button tap, not the dialog "close" event (some browsers skip that event). Pass `note` when it can be undone (Recently deleted).
- Everything user-entered that goes into `innerHTML` must pass through `esc()`.
- BMI ranges are WHO adult cut-offs (18.5 / 25 / 30); the footer also mentions the Asian 22.9 cut-off. Goal pace is `PACE` kg/week, weekly exercise target is `WEEKLY_MINUTES`.
- If you add or rename a file in `public/`, add it to `SHELL` in `sw.js` and bump `CACHE` (e.g. `journal-v2` → `journal-v3`).
- **Every saved doc is dated** so the data can be analysed later: day records carry `date` (`YYYY-MM-DD`) plus a ms time (`at`, or `created` / `updated`; entries also `moodAt`); library docs (foods, meal sets, kinds, pantry, diary photos) carry `created` / `updated`. Keep `created` when re-saving. New collections must do the same.
- Dates are local-time `YYYY-MM-DD` strings; use the `iso` / `parse` / `dayNum` helpers rather than `Date` parsing.
- UI copy is plain and short, written for two non-technical users on phones. Check layouts at phone width.
